# CLI 上下文交接（context handoff）方案

> 状态：**已搁置**（2026-09 记录，未实现）。背景见会话讨论，本文件保留设计意图与取舍，供后续实现参考。

## 动机

REPL 窗口快满时，当前做法是**压缩**（shadow 最旧 + 裁剪大工具结果）。但对于**长任务**，压缩并不理想：

- 长任务多是顺序推进（"处理 100 个文件"），模型只需要"目标 + 当前项 + 进度"，不需要持续持有全部历史。
- 压缩是**隐式丢失**：旧细节从主动上下文消失，模型无法按需取回。

## 提议方案

窗口接近上限时**不压缩**，改为**上下文接力**：

1. **新开一个上下文**（新 session log）。
2. **冷启动交接简报**：把"任务目标 + 进度摘要 + 关键过程 + 产出 + 来源 session id"作为 `system.context` 注入新会话。
3. **历史下钻工具**：提供 `read_session` 类工具，让新上下文**按需取回**旧会话的原文细节。

## 与压缩的取舍

| 维度 | 压缩（现状） | 交接 + 下钻 |
|---|---|---|
| 主动上下文 | 单一连续线程，旧信息被 shadow/裁剪 | 干净（当前任务 + 简报） |
| 旧细节 | 丢失 | **按需取回**（下钻）——核心优势 |
| 交接质量 | 隐式截断 | 显式简报（可生成、可人工审） |
| 成本 | 每轮一点 | 交接一次 + 每次下钻一次模型往返 |
| 适合 | 短/中会话、需持续记忆 | 长目标导向、顺序推进任务 |

例外：**记忆密集任务**（大范围重构、需始终握着全局设计）交接 + 下钻反而更费（下钻是往返，模型还得主动想起去查）。

## 风险与问题

1. **交接质量是成败关键**：简报写不好，新上下文从开头就懵。需要一次显式摘要调用，prompt 要刻意设计。
2. **下钻工具的边界**：
   - 权限：历史会话含完整文件内容/工具结果/可能密钥 → 只允许读**本接力链**的会话，不能任读。
   - 上下文回涨：下钻返回要**有界**（head+tail 裁剪、限量），否则白接。
   - 会话选择：简报必须带来源 session id，避免模糊搜索。
3. **触发时机**：窗口硬触发可能断任务中途 → 建议人工 `/continue` 或任务边界自动。
4. **会话蔓延**：长任务拆成多会话，需要**谱系**（`parent_session`）、命名与清理。
5. **延迟**：下钻是额外模型往返，长任务里要算总账。

## 建议落地方案

与现有事件溯源架构拼装：

1. `/continue`：蒸馏当前会话 → 交接简报（目标/进度/产出/来源 id）→ 新会话 seed `[默认定位, 简报, agent.md]` → 旧会话记 `parent_session`。
2. `read_session` 工具：只读本链会话，有界返回（head+tail、限量），可选关键词定位。
3. 压缩保留给小/中会话（或可配置关闭），长任务用接力。
